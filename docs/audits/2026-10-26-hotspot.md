# Hotspot: audit, fix and the device test script (26 October 2026)

Owner: "hotspot is not working". Branch `feat/hotspot-working`, cut from `feat/android-only` (PR #266). Written by the
hotspot-engineer role (audit, plan, apply, test) and checked by the orchestrator gate.

## Why it did not work (found in the code, reproduced on the old code)

| # | Cause | Evidence |
|---|---|---|
| 1 | **A guest looked for the host at the ".1" of its network. Stock Android does not use ".1".** Android 9 gives the hotspot `192.168.43.<random>` (the last number is random and never 0, 1, 42 or 255; older releases use the same class, not read); Android 11 gives `192.168.<random>.<random>` (last number random, 0, 1 and 255 replaced). ## The design (smallest with no vendor assumption)

* **Host**: the room server (WebSocket, unchanged) plus `HotspotBeacon`, a UDP socket on `discovery_port` (8081) that answers the
  fixed text `kalyeah?` with `kalyeah!` to whoever asked. Nothing from the network is decoded.
* **Guest**: `HotspotFinder` sends `kalyeah?` out of each Wi-Fi address, to `255.255.255.255` and to the `.255` of its /24, every
  second for 5 s. Each phone that answers is asked for its room over the existing WebSocket handshake (`DISCOVER_ROOM`); only a
  `ready` room is joined. The old guesses (the ".1" of each network, 192.168.43.1, 172.20.10.1) run side by side as a fallback.
* **Modals** (`HotspotDialogs` + `HotspotFlow`): Create checks the hotspot is on; Join checks the Wi-Fi, searches, and joins the
  verified room. Both: Try again, Cancel, Back, automatic re-check when the app returns from the phone's settings, a failure line
  with the phone's network, and nothing runs or calls back after the dialog is closed.
* **Rule for "hotspot on" and "on a Wi-Fi"** (`HotspotNet`): every interface is a *client* (`wlan0`, `eth0`), *ignored* (loopback,
  mobile data `rmnet`/`ccmni`/..., VPN, Wi-Fi Direct) or a *tether* (any other name). Hotspot on = a tether has a private IPv4.
  Wi-Fi connected = a client has one. The names are data (`data/rules/net_rules.tres`). A negative list was chosen over a list
  of access-point names (`ap0`, `swlan0`, `softap0`, `wlan1`...) because vendor names cannot be enumerated: an unknown name is
  taken for a tether, which at worst lets Create go on where Create would have been refused.
* **Rejected**: guessing more gateways (cannot work, see 1); scanning the whole /24 over WebSocket (254 sockets, only /24);
  mDNS/multicast (needs the multicast lock and many routers drop it; broadcast is simpler); a `WifiManager` call through JNI to ask
  "is the hotspot on" (hidden API, permissions); a typed code or address (owner rule); a "my hotspot is on" override button
  (breaks "never create a room when it is off").
* **Permission added**: `CHANGE_WIFI_MULTICAST_STATE` (normal, no prompt). Proof it is needed: Godot 4.6.2 enables the Wi-Fi multicast
  lock when a UDP socket enables broadcast (`NetSocketAndroid::set_broadcasting_enabled`) and `GodotNetUtils` creates that lock only
  if the permission is declared ("needed on some devices to receive broadcast and multicast packets"); the `PacketPeerUDP`
  documentation says the same. The host receives the broadcast. `ACCESS_WIFI_STATE`, location and `NEARBY_WIFI_DEVICES` are not needed.
* **Settings button**: "Hotspot settings" on the off modal opens Android's "Network & internet" screen
  (`android.settings.WIRELESS_SETTINGS`, public) through `AndroidRuntime.getActivity()` and `JavaClassWrapper` (both in 4.6.2, read
  in `AndroidRuntimePlugin.kt` and the `JavaClassWrapper` docs). No permission. It exists only where those singletons exist; it
  is a device check.

## Assumptions

| Assumption | Status |
|---|---|
| The host is the ".1" of the guest's /24 | **False** on stock Android 9 and 11 (AOSP sources above). Fixed: discovery does not use the address. |
| A hotspot is a /24 | True in AOSP 9 and 11 (`PREFIX_LENGTH = 24`). Other sizes (OEM /23, /16): **guess**; the limited broadcast leaves by the interface whatever the mask. Device check. |
| Any private IPv4 means a hotspot | **False** (old code run). Fixed by the interface roles; tested on 17 interface lists (one capture, sixteen synthetic). |
| Interface names of access points (`ap0`, `swlan0`, `softap0`, `wlan1`, `rndis0`, `bt-pan`) | From memory, **synthetic** (labelled so in `tests/unit/hotspot_phones.gd`; only the container list is a capture). The rule does not depend on them except `wlan0` (client) and the ignored prefixes. |
| `wlan0` is the Wi-Fi client on every phone | **Guess**, true on AOSP. A phone whose hotspot uses `wlan0` (single-radio, old Qualcomm) would be seen as "hotspot off". Device check: the failure line shows it. |
| `IP.get_local_interfaces()` lists all interfaces on Android 7 to 15 | **Guess** (Godot reads `getifaddrs`). If a phone returns nothing, the failure line says "no network address". Device check. |
| A UDP socket bound to an interface address sends the limited broadcast out of that interface | Linux behaviour, **verified on loopback** here (bound to 127.0.0.1, sent to 255.255.255.255 and 127.255.255.255, a socket on 0.0.0.0 received both; integration tests). Android's per-network routing is a **device check** (Wi-Fi without internet while mobile data is on). |
| The host hears a broadcast on Wi-Fi | Godot docs and source: needs the multicast lock on some devices; permission added. Whether a given chip filters: **device check**. |
| `ws://` to a private address is allowed on Android 9+ | Cleartext policy governs the Java HTTP stack, Godot opens native sockets: **unverified**, device check (the old design already depended on it). |
| Host server binds all interfaces, one port, stops on leaving, can start again | **Verified** (docs, `Net.stop_host` on Back and on the title screen, start-stop-start test). |
| A backgrounded host keeps answering | **No**: Godot's main loop pauses with the app, so the host must stay in front. Device check (test 8). Not fixed: a foreground service needs permissions and a Java plugin; out of scope and not needed to play in one place. |
| AP/client isolation off | Hotspots do not isolate; routers may. Device check. |

## What the tests prove, and what they cannot

Container proof (full suite 95 scripts, 1063 tests, 1062 passing, 3 pending that were already pending; baseline 94 / 1025 / 1024 / 3):
`tests/unit/test_hotspot_net.gd` (the rule on 16 interface lists, plan, failure line), `tests/integration/test_hotspot_discovery.gd`
(real host and real guest on loopback: found by limited broadcast with no candidate, by directed broadcast, by the fallback alone,
no host, host without room ends early, full, in progress, other version, host stops while searching, two hosts, host restarts,
`Net.start_host` three times, the beacon ignores junk and obeys its burst, the guest joins the found room), `tests/unit/test_hotspot_dialogs.gd`
(every modal state, Try again, Cancel, Back, resume, settings button, no callback after close, no hang), title and lobby tests.
They **cannot** prove: the access point's real address and mask, Wi-Fi broadcast filtering, Android routing, `getifaddrs` on
each Android version, the settings intent, phone speed. That is what the script below is for.

## Device test script (owner, 2 or 3 phones)

Install the APK of the `Android APK` run on branch `feat/hotspot-working` on every phone. Phone **A** = stock Android (Pixel, Motorola,
Nokia). **B** = a phone with a maker skin (Samsung One UI, Xiaomi, Oppo, Realme, Huawei). **C** = any third phone (guest). For every
test note: phone model, Android version, skin, mobile data on or off. When something fails, **photograph the whole modal**: its last
two lines ("This phone: ..." and "Asked N · answered M") are how a failure is diagnosed.

1. **Create, hotspot off.** On A: Wi-Fi off, hotspot off. Hotspot, Create room. Expect "Your hotspot is off. Turn it on, then tap Try again.", buttons Hotspot settings, Try again, Cancel. No room screen. Tap Hotspot settings: Android's network settings open (report if not). Come back: it re-checks by itself and says off again. Cancel.
2. **Create on an ordinary Wi-Fi.** A on a home Wi-Fi, hotspot off: Create must say the hotspot is off (it used to create a room).
3. **Create, hotspot on.** Turn A's hotspot on. Create room. Expect: no message, the room screen with you as host. If it says off with the hotspot on, photograph it (the interface name is what is missing). Repeat on B.
4. **Join, no Wi-Fi.** On C: Wi-Fi off. Join room. Expect "Connect to your friend's hotspot in Wi-Fi settings, then tap Try again."
5. **Join, no room yet.** C joins A's hotspot (Wi-Fi settings), then Join room while A is only on the home screen. Expect "Looking for a room…" then, within about 5 s, "No room found. Ask your friend to tap Create room, then tap Try again." Now A taps Create room, C taps Try again: C joins within about 2 s. Count: both names in the room.
6. **Join, room ready first.** A creates, then C taps Join room: joins. Note seconds from tap to lobby. Repeat with B as host and C as guest, and B as guest of A.
7. **Messages.** With a 1v1 room (2 players) a third phone sees "That room is full."; after A starts a match, "That match has already started."
8. **Host leaves and creates again.** A: Back (leave), Create room again; C Join again. Works the second time?
9. **Host in the background.** A and C in the room; A presses Home for 10 s and returns. Does C stay in the room, or is it dropped? Report.
10. **Mobile data.** Repeat 5 and 6 with mobile data off on C, then on. If it works only with data off, report (Android sends the app's traffic over mobile data when the Wi-Fi has no internet).
11. **Optional, shared router.** A on the home Wi-Fi with its hotspot also on (if the phone allows both), C on the same home Wi-Fi: Join should find A through the router.

Report back for each failure: the test number, the photo of the modal, phone model and Android version, mobile data state.
How to read it: *"This phone: wlan0 ..." only, hotspot on* = the phone's hotspot uses `wlan0` (rule gap); *"no network address"* = the phone hides
interfaces from apps; *Asked N · answered 0* with the host in a room = the broadcast did not arrive (isolation, filtering, routing);
*answered 1* but no room = the host answered but its WebSocket port is unreachable.
